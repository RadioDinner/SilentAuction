b. DIRECTIONAL DECISIONS
------------------------
Confirmed with the user via clarifying questions:
  1. BID ENTRY: staff edit the Google Sheet directly (the sheet IS the admin
     interface). No custom admin page, no DB. Dashboard reads the sheet.
  2. TICKETS: highest bid closes first (descending), one active countdown at a
     time, a bid on the active ticket extends ALL remaining tickets by 1 min.
  3. TICKET TIMING: next ticket's countdown auto-starts when the previous
     closes; fixed configurable length (ticket_countdown_seconds).

Architecture decisions:
  - Stack: Next.js (App Router) on Vercel. Google Sheets API via service
    account (read-only). Polling (default 3s) instead of websockets — simpler,
    robust for a one-day event.
  - All auction rules live SERVER-SIDE in lib/auction.ts as a PURE, STATELESS
    function of (sheet data + current time). No stored cascade state, so any
    reload yields the correct picture. This is the key design choice.
  - Anti-snipe (regular items): effectiveClose = max(scheduledClose,
    lastBidTime + window). Default window 60s. Matches the 5:30->5:31 example.
  - Ticket cascade: tickets sorted by bid desc; close[i] = (i==0 ? cascadeStart
    : close[i-1] + countdown), then anti-snipe max() per ticket. Because later
    closes derive from earlier ones, extending the active ticket shifts all
    remaining tickets by the same amount automatically.
  - Bid timing source: Apps Script auto-stamps "Last Bid Time" on bid edits, so
    staff only type the amount. Manual entry also supported.
  - SUPABASE NOTE: the New Session Instructions mention Supabase migration
    numbering, but this project uses Google Sheets per the user's explicit
    choice. No Supabase/DB is used. supabase/migrations/ does NOT exist. If a DB
    is ever introduced, revisit.
